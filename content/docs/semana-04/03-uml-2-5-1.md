## 1. Material

### 1.1 O que é UML (leitura de prova)

**UML** (*Unified Modeling Language*) é uma **linguagem padronizada de modelagem** (OMG) para visualizar, especificar, construir e documentar artefatos de sistemas de software — **não** é metodologia de processo (não é Scrum, não é RUP por si só).

Três âncoras mentais:

| Âncora | Frase cobrável |
|--------|----------------|
| Papel | **Notação** comum para diagramas (estrutura e comportamento) |
| Versão no edital | **UML 2.5.1** (reconheça o número) |
| Limite | Modela; **não** substitui elicitation de requisitos nem implementação |

Flash: enunciado fala em **diagrama de classes / casos de uso / sequência / atividades**, **ator**, **associação**, **UML 2.5.1** → **UML**.

UML **não** é: BPMN (processo de negócio — notação distinta), Docker, CMMI, linguagem de programação.

### 1.2 Por que a FCC cita 2.5.1

1. Edital amarra **MR-MPS-SW 2024 e UML 2.5.1** no bloco de processo de desenvolvimento.  
2. Prova cobra **reconhecer diagramas** e **relações**, não desenhar ferramenta CASE.  
3. Liga modelagem a **requisitos** (casos de uso) e a **projeto** (classes, sequência).  
4. Evita confusão com versões antigas “UML 1.x” em itens de atualidade de edital.

Frase: saber **2.5.1** + **tipos de diagrama** + **para que serve cada um**.

### 1.3 Estrutural × comportamental (tabela ouro)

| Família | Foco | Exemplos cobráveis |
|---------|------|--------------------|
| **Estrutural (estático)** | **O que** existe — elementos e relações | Classes, objetos, componentes, pacotes, implantação, perfil, estrutura composta |
| **Comportamental (dinâmico)** | **Como** se comporta no tempo | Casos de uso, atividades, máquina de estados, interação (sequência, comunicação, timing, overview) |

Flash:

- Estrutura = **foto** do sistema.  
- Comportamento = **filme** / interação no tempo.

Armadilha: dizer que diagrama de classes mostra a ordem temporal das mensagens (isso é **sequência**).

### 1.4 Diagrama de casos de uso (visão cobrável)

**Casos de uso** modelam **funcionalidades** vistas pelos **atores** (usuário ou sistema externo).

| Peça | Papel |
|------|-------|
| **Ator** | Papel externo que interage com o sistema |
| **Caso de uso** | Unidade de funcionalidade (“Autenticar”, “Consultar processo”) |
| **Associação** | Ligação ator ↔ caso de uso |
| **Include («include»)** | Comportamento **obrigatório** reutilizado (base sempre inclui) |
| **Extend («extend»)** | Comportamento **opcional/condicional** que estende o base |
| **Generalização** | Ator ou caso de uso mais específico herda do geral |

Flash include × extend (clássico FCC):

| | **Include** | **Extend** |
|---|-------------|------------|
| Natureza | Obrigatório / fatoração comum | Opcional / sob condição |
| Direção mental | Base **inclui** o incluído | Extensão **estende** o base |

Erro clássico: inverter include e extend.

### 1.5 Diagrama de classes (estrutura ouro)

Mostra **classes**, atributos, operações e **relacionamentos**.

| Relação | Ideia cobrável |
|---------|----------------|
| **Associação** | Ligação estrutural (pode ter multiplicidade 1, 0..1, 1..*, *) |
| **Agregação** | “Todo–parte” **fraca** (parte pode existir sem o todo — losango vazio, visão clássica) |
| **Composição** | “Todo–parte” **forte** (parte vive/morre com o todo — losango preenchido) |
| **Generalização / herança** | “é um” (seta para a superclasse) |
| **Dependência** | Uso pontual / mudança em A pode afetar B |
| **Realização** | Classe realiza interface |

Multiplicidade: quantos objetos de um lado se relacionam com o outro.

Armadilha: trocar **composição** (forte) por **agregação** (fraca).

### 1.6 Diagrama de sequência (interação)

Mostra **troca de mensagens** entre objetos/linhas de vida **no tempo** (eixo vertical = tempo).

| Elemento | Leitura |
|----------|---------|
| Linha de vida | Objeto/ator participantes |
| Mensagem síncrona / assíncrona | Chamada que espera / não espera (visão) |
| Retorno | Resultado da chamada |
| Fragmentos (alt, loop, opt…) | Alternativa, repetição, opcional — nomes para reconhecer |

Quando a prova fala em **ordem temporal** de chamadas entre objetos → **sequência** (não classes).

### 1.7 Diagrama de atividades

Modela **fluxo de controle/dados** de um processo ou algoritmo (nós de ação, decisões, paralelos/fork-join, início/fim).

Contraste leve com BPMN:

| | **Atividades (UML)** | **BPMN** |
|--|----------------------|----------|
| Origem | UML (software/comportamento) | Notação de **processo de negócio** |
| Uso típico de prova | Fluxo interno / workflow de sistema | Processos organizacionais / negócio |

Podem se complementar; **não** são a mesma notação.

### 1.8 Máquina de estados (visão)

Estados de um objeto + transições por eventos. Útil quando o ciclo de vida importa (ex.: petição: rascunho → protocolada → conclusa).

Flash: “estados e eventos” → máquina de estados; “mensagens entre objetos no tempo” → sequência.

### 1.9 Componentes, pacotes e implantação (estrutura de arquitetura)

| Diagrama | Foco |
|----------|------|
| **Componentes** | Módulos/componentes e interfaces (visão de arquitetura de software) |
| **Pacotes** | Organização/agrupamento de elementos (namespaces lógicos) |
| **Implantação (deployment)** | Nós físicos/ambientes e artefatos implantados |

Encaixe mental PDPJ: componentes/implantação **modelam** distribuição; Docker/K8s **executam** — papéis diferentes.

### 1.10 Outros diagramas (margem — reconhecer nome)

Não precisa aprofundar todos; saber que existem na família UML 2:

- Objetos, estrutura composta, perfil (estruturais)  
- Comunicação, timing, interaction overview (interação)  
- Visão geral: a prova foca **casos de uso, classes, sequência, atividades** com mais frequência

### 1.11 UML × requisitos × ágeis (ponte)

| Tema | Relação |
|------|---------|
| Engenharia de requisitos | Casos de uso / histórias **especificam**; UML **modela** |
| Ágil | UML pode ser **leve** (whiteboard, só o necessário); não é proibida |
| CMMI/MPS/ISO | Processos podem exigir modelagem; UML é **linguagem**, não o processo |
| Código | Modelo guia implementação; não substitui testes |

Armadilha: “UML = metodologia completa de projeto” — **falso**.

### 1.12 Visão 4+1 (Racional) — flash opcional

Conjuntos de vistas (lógica, processo, desenvolvimento, física + cenários/casos de uso). Serve só para item que cite “visões arquiteturais”; não decore artigo a artigo.

### 1.13 Boas práticas cobráveis (lista seca)

1. Escolher o diagrama pelo **objetivo** da pergunta.  
2. Manter modelo **consistente** com requisitos.  
3. Não modelar tudo com o mesmo diagrama.  
4. Nomear atores/casos de uso de forma clara.  
5. Usar multiplicidades corretas.  
6. Separar include/extend.  
7. Lembrar: modelo ≠ código compilado.  
8. Versão do edital: **2.5.1**.

### 1.14 O que UML **não** é (lista seca)

1. Não é BPMN.  
2. Não é Scrum/Kanban/XP.  
3. Não é CMMI nem MPS-SW.  
4. Não é linguagem de programação.  
5. Não é ferramenta CASE específica (Enterprise Architect etc. — só suporte).  
6. Não elimina engenharia de requisitos.  
7. Não é Docker/Kubernetes.  
8. Não é ITIL/COBIT.

### 1.15 Armadilhas FCC (lista de ouro)

1. Trocar **include** por **extend**.  
2. Trocar **agregação** por **composição**.  
3. Usar diagrama de **classes** onde cabe **sequência** (ordem temporal).  
4. Dizer que UML é **processo** de desenvolvimento.  
5. Confundir UML com **BPMN**.  
6. Ignorar a versão **2.5.1** do edital.  
7. Achar que ator = sempre pessoa física (pode ser sistema externo).  
8. Confundir pacote com componente com nó de implantação.  
9. Tratar UML como obrigatória em **todo** artefato ágil.  
10. Reduzir UML a “só diagrama de classes”.

### 1.16 Mini-síntese (cartão mental)

> **UML 2.5.1** = linguagem de **modelagem** (OMG), não metodologia.  
> **Estrutural** = classes, componentes, pacotes, implantação…  
> **Comportamental** = casos de uso, sequência, atividades, estados…  
> **Include** obrigatório; **extend** opcional/condicional.  
> **Composição** forte; **agregação** fraca.  
> Sequência = mensagens no **tempo**.  
> Complementa requisitos; distingue-se de BPMN e de ágeis/CMMI.

## 4. Auto-checagem rápida (opcional)

Antes de marcar a questão, pergunte:

1. É **notação/diagramas de software**, versão **2.5.1**? → UML.  
2. É **estrutura** (classes, pacotes, componentes, nós)? → Estrutural.  
3. É **tempo/fluxo/estados/casos de uso**? → Comportamental.  
4. É **obrigatório comum** vs **opcional** em casos de uso? → Include × extend.  
5. É **todo–parte forte** vs **fraco**? → Composição × agregação.  
6. É **processo de negócio** (BPMN)? → Não é UML.  
7. É **elicitar/validar/gerenciar requisitos**? → Arquivo 02.  
8. É **Scrum/Kanban**? → Método ágil, não UML.
