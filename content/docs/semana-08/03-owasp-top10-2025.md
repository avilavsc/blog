## 1. Material

### 1.1 O que a FCC realmente pergunta

| Padrão de item | Exemplo |
|----------------|---------|
| “Número 1 da lista…” | Descrever sintoma de **Broken Access Control** (FCC TRF4/2025 ainda citou **2021**, mas A01 continua #1 em 2025) |
| Prevenção de SQL Injection | **Prepared statements** / parâmetros (FCC TRT15/2024); whitelist no **servidor** (FCC TJ-CE/2022) |
| Troca de categoria | Descrição de Injection no lugar de Access Control; Misconfig no lugar de Supply Chain |
| Framework seguro | NIST SSDF / SDL / OWASP Top 10 como **complemento** (FCC TRT-2/2025 — linha desenvolvimento seguro) |

Flash de prova: edital TRT4 01/2026 pede **2025**; provas recentes FCC ainda rotulam **2021**. Estude **2025** como lista principal e saiba o **delta** para não errar quando o enunciado citar ano antigo.

### 1.2 Frase-âncora

> O OWASP Top 10 é documento de **conscientização** sobre os riscos de segurança mais críticos em **aplicações web**, baseado em dados de testes + pesquisa da comunidade — **não** é lei, **não** substitui LGPD/ISO, e **não** é checklist único de auditoria.

### 1.4 O que mudou: 2021 → 2025 (cartão anti-confusão)

| Movimento | Detalhe cobrável |
|-----------|------------------|
| **A01** | Continua #1; **SSRF** foi **incorporado** a Broken Access Control (antes categoria própria A10:2021) |
| **A02** | Misconfiguration sobe de #5 (2021) para **#2** (2025) — software cada vez mais “config-driven” |
| **A03** | **Nova amplitude:** expande *Vulnerable and Outdated Components* (A06:2021) para **toda** a supply chain (deps, build, CI/CD, distribuição) |
| **A04 / A05** | Cryptographic Failures e Injection **descem** duas posições (#2→#4 e #3→#5), mantendo ordem relativa |
| **A06** | Insecure Design escorrega (#4→#6) |
| **A07** | Mesma posição; nome enxuga de *Identification and Authentication Failures* → **Authentication Failures** |
| **A08** | Mantém #8 — integridade em nível de artefato/confiança (abaixo da supply chain “ecossistema”) |
| **A09** | Mantém #9; *Monitoring* → ênfase em **Alerting** (log sem alerta ≈ valor mínimo) |
| **A10** | **Nova:** *Mishandling of Exceptional Conditions* (erro/fail-open/lógica sob condições anormais). Sai SSRF como categoria solo |

**Duas novidades / um consolidado (visão OWASP):** (1) Supply Chain Failures ampliada; (2) Exceptional Conditions nova; (3) SSRF consolidado em A01.

### 1.5 A01 — Broken Access Control

**Ideia:** a aplicação não impõe corretamente o que o usuário **pode** ver/fazer (horizontal/vertical, IDOR, força de métodos HTTP, CORS permissivo, CSRF, elevação de privilégio). Em 2025, inclui **SSRF** (servidor faz requisição a recurso interno/indesejado a mando do atacante).

**Sintomas cobráveis FCC (TRF4/2025, lista 2021 #1 — ainda válido para A01:2025):**

- falta de restrição a métodos **POST/PUT/DELETE** para quem não deveria  
- manipulação de ID de objeto (acessar recurso de outro usuário)  
- metadados JWT/cookie alteráveis sem verificação server-side  

**Mitigações:** deny by default; checagem de autorização **no servidor** em cada path; ownership checks; desabilitar listagem de diretórios; CSRF tokens em estado mutável; rate limit; para SSRF — allowlist de destinos, bloquear ranges privados, não concatenar URL crua do usuário.

**Distrator:** “falta sanitizar input” → isso é **Injection (A05)**, não A01.

### 1.6 A02 — Security Misconfiguration

**Ideia:** stack insegura por padrão ou por descuido: contas default, diretórios abertos, headers ausentes, cloud buckets públicos, XXE por parser XML permissivo, ambientes de debug em produção, permissões IAM excessivas.

**Por que subiu:** apps modernas expõem mais superfície via **configuração** (flags, YAML, feature toggles, PaaS).

**Mitigações:** hardening repetível (IaC); remover features não usadas; banners/erros sem stack trace; patch de plataforma; revisão de permissões cloud; desabilitar verbos HTTP desnecessários.

**Distrator:** “biblioteca desatualizada no pom.xml” → mais **A03** (componente/cadeia) do que misconfig pura — embora possam coexistir.

### 1.7 A03 — Software Supply Chain Failures

**Ideia:** falha em **construir, distribuir ou atualizar** software com confiança — deps vulneráveis/maliciosas, CI/CD fraco, registry comprometido, falta de SBOM, promoção sem four-eyes, imagens base não assinadas.

**Além de “lib velha”:** IDE extensions, artifact repos, pipelines com secret amplo, dependências **transitivas**.

**Mitigações:** inventário + SBOM; Dependency-Check/Track; fontes oficiais assinadas; pin de versões; separar quem commita de quem promove a prod; hardening do pipeline; remover deps mortas; patch risk-based.

**FCC antiga:** “falta testar compatibilidade de libs atualizadas” caía em *Vulnerable Components* — hoje encaixa em A03.

### 1.8 A04 — Cryptographic Failures

**Ideia:** falha na **proteção criptográfica** (causa-raiz) que leva a exposição de dados sensíveis: HTTP sem TLS, algoritmos fracos (MD5/SHA-1 para senha), IV/nonce reutilizado, chave hardcoded, armazenamento de senha sem KDF adequado (bcrypt/scrypt/Argon2), padding oracle, etc.

**Mitigações:** TLS 1.2+ (preferir 1.3); classificar dados; crypto moderna; gerenciar chaves fora do código; nunca inventar protocolo.

**Distrator LGPD:** “falha cripto” ≠ ausência de base legal — são eixos distintos (arquivo 02 × este).

### 1.9 A05 — Injection

**Ideia:** dados não confiáveis interpretados como **comando/consulta**: SQL, NoSQL, OS command, LDAP, EL/OGNL, e **XSS** (na taxonomia 2021 XSS era A07; em 2025 XSS permanece sob o “guarda-chuva” Injection nas CWEs de injeção — a FCC ainda pode falar XSS separado; trate XSS como injeção no browser).

**Prevenção que a FCC ama:**

| Faça | Não faça |
|------|----------|
| Prepared statements / bind parameters | Concatenar SQL com input |
| Whitelist de validação **no servidor** | Confiar só em validação JS no cliente |
| Escape contextual de output (XSS) | `innerHTML` com input cru |
| ORM com queries parametrizadas | “ORM = proibido” (distrator TJ-CE) |

**FCC TRT15/2024:** técnica mais adequada contra SQLi → **utilizar parâmetros (prepared statements)**.  
**FCC TJ-CE/2022:** validação no servidor com **whitelists** (não “só no cliente”).

### 1.10 A06 — Insecure Design

**Ideia:** falha de **arquitetura/ameaça** — não é bug de implementação isolado. Falta threat modeling, limites de negócio, segregação, pressupostos ingênuos (“usuário não vai chamar a API direta”).

**Mitigações:** modelagem de ameaças; secure design patterns; story de abuso; limites (quota, workflow); “assume breach” no desenho.

**Distrator:** patch pontual de SQLi sem redesenhar trust boundary continua sendo A05; A06 é quando o **modelo** é frágil.

### 1.11 A07 — Authentication Failures

**Ideia:** autenticação quebrada — senhas default, credential stuffing sem defesa, session fixation, tokens previsíveis, “esqueci senha” fraco, ausência de MFA onde o risco exige, recuperação por conhecimento compartilhável.

**Mitigações:** frameworks maduros (não reinventar); MFA; mensagens de erro genéricas; rotação/invalidação de sessão no login; proteção contra stuffing (rate limit, hibp); armazenar senha com KDF.

**Nome:** 2025 dropa “Identification and…” — foque em **Authentication Failures**.

### 1.12 A08 — Software or Data Integrity Failures

**Ideia:** quebra de **confiança/integridade** de artefatos e dados em nível mais “local” que A03: update sem verificação de assinatura, desserialização insegura, CI que puxa build sem checksum, auto-update unsigned, CDN sem SRI, pipeline que aceita plugin não confiável.

**A03 × A08 (prova):**

| | A03 Supply Chain | A08 Integrity |
|--|------------------|---------------|
| Foco | Ecossistema (deps, build, distribuição) | Verificar integridade / trust boundary do artefato/dado |
| Exemplo | pacote npm malicious no registry | desserializar objeto não confiável; update sem assinatura |

### 1.13 A09 — Security Logging & Alerting Failures

**Ideia:** eventos auditáveis não logados, logs sem proteção, ou — ênfase 2025 — **sem alerta** que provoque ação. Login fail, mudança de privilégio, exportação em massa, erro de validação repetido: se ninguém é acordado, o log é decorativo.

**Mitigações:** logar autenticação, acesso privilegiado, falhas de input relevantes; proteger logs (integridade, ACL); alertas com playbook; evitar PII/senha no log (amarra LGPD).

**Distrator FCC:** “existência de eventos auditáveis não registrados” descreve A09 — não A01.

### 1.14 A10 — Mishandling of Exceptional Conditions (**novo 2025**)

**Ideia:** o sistema não previne, não detecta ou **responde mal** a condições anormais: fail-open em authz, stack trace com segredo (CWE-209), null deref, recurso esgotado, race, parâmetro ausente tratado como sucesso, catch genérico que engole erro de segurança.

**Tríade OWASP:** (1) não impedir a situação excepcional; (2) não reconhecê-la; (3) não tratar / tratar de forma insegura.

**Mitigações:** fail **secure** (fechado); handler local + global; mensagens seguras ao usuário; log + alerta; testes de falha/chaos leve; validar cedo; limites de recurso.

**Distrator:** A10:2021 era **SSRF** — em 2025 SSRF → A01; A10 novo ≠ SSRF.

### 1.15 Desenvolvimento seguro — encaixe FCC

| Prática | Onde aparece |
|---------|--------------|
| Controle de acesso + validação **server-side** | A01, A05 |
| Prepared statements / ORM seguro | A05 |
| Threat modeling / secure design | A06 |
| SBOM, pin, pipeline harden | A03, A08 |
| TLS, KDF, key mgmt | A04 |
| MFA, session mgmt | A07 |
| Log + **alerta** | A09 |
| Fail closed, error handling | A10 |
| Hardening / defaults seguros | A02 |

**FCC TRT-2/2025 (linha):** adotar framework tipo **NIST SSDF** (“Preparar a Organização”, “Proteger o Software”) **e** complementar com OWASP Top 10 para vulnerabilidades web críticas — em oposição a “só front-end”, “só CLASP focado em config”, “testes de segurança dispensáveis se houver try/catch”.

### 1.16 Mapa 30 segundos (antes da prova)

```
A01 Acesso (IDOR, métodos, CSRF, SSRF)
A02 Config (default, cloud, headers, XXE)
A03 Cadeia (deps, CI/CD, SBOM)
A04 Cripto (TLS, algs, chaves, senhas)
A05 Injection (SQL, cmd, XSS…)
A06 Design (ameaça, modelo)
A07 Authn (sessão, MFA, stuffing)
A08 Integridade (assinatura, deserialize)
A09 Log + Alerta
A10 Exceções (fail-open, erro inseguro)
```
